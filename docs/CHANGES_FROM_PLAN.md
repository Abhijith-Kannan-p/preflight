# Changes from the Round 1 plan

Each change from the Round 1 plan, with the reason. Kept short and honest.

| Area | Round 1 plan | Round 2 build | Why |
|---|---|---|---|
| Demo users | Three roles plus admin | Added a seeded **Reviewer** (abhi2) alongside Creator, Brand Manager, Approver and Admin | The permission table has a Reviewer column; a seeded reviewer lets judges see the "Needs a human look" queue |
| Demo user names | Riya Sharma, Arjun Mehta, Neha Iyer, Admin | **abhi1** (Creator), **abhi2** (Reviewer), **abhi3** (Brand Manager), **abhi4** (Approver), **abhi5** (Admin) | The author's preference: neutral demo identities |
| Frontend framework version | Next.js 14+ | Next.js 15.5 | The 15.1 template had published security advisories |
| Claim rules | CLM-01, 04, 06, 08 | Added **CLM-02** (contradicts an approved fact, critical), **CLM-03** (uses a superseded fact, major) and **CLM-05** (factual claim with no approved fact, major) | Every finding must cite a rule; the plan's verdicts `contradicted`, `outdated` and `unsupported` had no rule to cite |
| NLI model | DeBERTa-v3 NLI | `cross-encoder/nli-deberta-v3-xsmall`, run as its official **int8-quantised ONNX export** (`onnx/model_quint8_avx2.onnx`, 87 MB) with ONNX Runtime and SentencePiece; no PyTorch | Fits a 512 MB host. Same model and labels; probabilities within 0.03 of fp32 PyTorch, and the evaluation is unchanged at accuracy 0.92 |
| Verdict logic | NLI entailment ≥ 0.7 decides `supported` | Same, plus a **deterministic support path**: if NLI is inconclusive but the numbers match exactly (or a verbatim quote covers most of the claim) on a clearly on-topic fact with no contradiction, the claim is `supported` at confidence 0.75 | The small NLI model rejects true paraphrases that add harmless detail ("…on your purchases"). The path never involves the LLM, keeps the quote check, and is visible in "How this verdict was reached" |
| Thresholds | Not specified | Topical-similarity gates for contradictions (numeric ≥ 0.74, NLI-only ≥ 0.75) | Calibrated on the labelled set: without them the model "contradicted" claims with loosely related facts. Calibrated on the same set we report on (no held-out split yet), noted in TECHNICAL.md |
| Finding merge | De-duplicate overlapping spans, keep highest severity | Merge only when findings cite the same rule on overlapping text, or cover nearly the same span (IoU ≥ 0.8) with the same type | Otherwise CLM-01 and CLM-04 on "India's #1 and 100% secure" collapse into one, and the plan's scenario expects both |
| Brand Score | Open findings only | Open findings, excluding those waiting in "Needs a human look" (confidence < 0.6) | Uncertain findings should not cost points until a person confirms them |
| Suggestions | LLM writes every suggestion | Brand-approved fallback wording from the rule (`fallback` in rules.csv) is used first; the LLM writes only what the rulebook has no wording for. "Free" (CLM-08) gets no rewrite, because the right fix is the offer disclaimer DSC-01 suggests | Safer (approved wording), faster (one fewer LLM round-trip, keeps a full review under 10 s) and stops euphemisms like "free" → "complimentary" |
| LLM model | Not fixed | Gemini `gemini-3.5-flash-lite` | Older Gemini models are retired; flash-lite answers JSON in 3–6 s, inside the 8 s timeout |
| Background jobs | Redis + RQ workers | In-process worker threads (one per review, own event loop) | Demo scale needs no queue; threads keep CPU-bound NLI off the API's event loop. A job queue can replace `runner.start_review` without touching the engine |
| Live progress | WebSocket | Server-Sent Events (`/api/reviews/{id}/events`) with replay of earlier events | Progress is one-way; SSE is simpler, proxies well and reconnects by itself |
| Disputes | Disputed critical findings block approval | Same, but a disputed critical **can be submitted**: the approver then either overrides it with a written reason (shown on the receipt) or requests changes | The dispute is a question for the approver; blocking submission would leave it nowhere to go |
| Readability library | textstat | textstat 0.7.4 (pyphen syllables) | Newer textstat downloads the CMU dictionary through NLTK at runtime (22 s, needs network) |
| Demo data | Pre-loaded brand, samples, users | Also a **generated review history**: on first boot (and after "Reset demo data") 8 fictional drafts from `data/seed/history.json` run through the real engine in deterministic mode, some fixed, disputed and approved, dated over the past three weeks. The evaluation is also precomputed at boot | Insights and Evaluation must show real numbers the moment a judge opens them |
| Public API | `POST /api/v1/preflight` with `{content \| file, channel}` | JSON `content` on `/api/v1/preflight`, uploads on `/api/v1/preflight/file` | A JSON body and a multipart upload are clearer as two documented endpoints |
| UI kit | shadcn/ui | Small hand-written Tailwind components (`components/ui.tsx`) on a warm paper theme | Fewer moving parts under deadline; same accessible patterns (native `<dialog>`, focus rings, tooltips on focus) |
| Diff viewer | react-diff-viewer | jsdiff word diff rendered inline | react-diff-viewer does not support React 19 |
| Python ML runtime | PyTorch + sentence-transformers, fastembed | **ONNX Runtime only**: both models are int8 ONNX files in lean sessions (graph optimisation off, no memory arena, one thread). PyTorch is optional (`NLI_BACKEND=torch`, `requirements-ml.txt`) | Measured in a container capped at 512 MiB: graph optimisation expanded the int8 NLI weights to 408 MiB at load (126 MiB without, identical outputs, ~20 % slower); fastembed's session cost 230 MiB vs 42 MiB for the same model's int8 file; the `tokenizers` DeBERTa vocabulary cost 106 MiB vs 56 MiB with SentencePiece (identical token ids) |
| Embedding model file | bge-small via fastembed | Same model, `Xenova/bge-small-en-v1.5` int8 ONNX export (34 MB), CLS pooling + L2 norm | Cosine 0.996 to the previous vectors; facts are re-embedded automatically whenever the embedding file changes. Evaluation re-run: accuracy 0.92, macro recall 0.90 (unchanged); `unsupported` precision 0.85 (was 0.86), contradicted recall 0.94 (was 0.97) |
| Backend hosting | Hugging Face Spaces or Render | **Render free plan** (512 MB RAM, 0.1 CPU, no card) via `render.yaml`; the Hugging Face Space package stays in `deploy/hf-space/` as an alternative | The new Hugging Face account hit "You've reached your CPU Basic quota limit". Render needs no card |
| Memory on the small host | Not specified | `MODEL_LOADING=lazy` (models load on the first review), `NLI_BATCH_SIZE=2` (DeBERTa's relative attention needs ~20 MiB per pair in flight: +308 MiB at batch 16), one inference at a time | Verified under `--memory=512m --cpus=0.1`: boot, history generation and a full LinkedIn review peak at **362 MiB** with no OOM; the unoptimised first attempt was OOM-killed at 503 MiB |
| Evaluation at boot | Precomputed at deploy | `EVAL_AT_BOOT=precomputed` loads `data/eval/precomputed_run.json`, produced by `python -m app.eval.run --export` with the same int8 models; the Run button still re-runs it live | 150 claims would take minutes on 0.1 CPU; the page must be ready the moment a judge opens it |

## Round 3 changes

| Area | Plan / spec | Delivered | Why |
|---|---|---|---|
| Demo data | One shared demo workspace | **A private copy per visitor** (httpOnly cookie, 24 h idle expiry). The five personas are copied with suffixed ids, so `user.workspace_id` scopes everything; audit chains are per workspace | Judges testing at the same time must not see or reset each other's work |
| Background jobs | One thread per review | A **job queue** with a small worker pool (`REVIEW_WORKERS`, 1 on Render), queue positions, re-queue after restart and a 120 s budget | Five simultaneous reviews must all finish, visibly, on a 0.1-CPU host |
| OCR engine | "Tesseract or PaddleOCR" (Round 2 plan) | **RapidOCR** (PaddleOCR PP-OCRv4 models on ONNX Runtime) | Render cannot install system packages (no Tesseract binary); no PyTorch |
| OCR detection size | RapidOCR's own `det_limit_side_len` | Overridden: detection on a 736 px copy (960 px for scans) | RapidOCR raises any "max" limit under 1500 px, so detection ran at full size: +230 MiB and 12 s on a scan at 0.1 CPU; 736 px costs +63 MiB and about 4 s and reads text as well |
| Memory with OCR | Not specified | `OCR_EXCLUSIVE=true` on Render: the NLI model is released while an image is read, `malloc_trim` after each review, `MALLOC_ARENA_MAX=2` | OCR beside NLI peaked at 504 MiB in a 512 MB container; with the swap the server's peak is 437 MiB |
| Brand book page references | Brand book of 8 to 12 pages (spec) | Rule citations run to page 19 (visual rules cite pp. 17–19) | Round 2 rules already cite pages up to 16; the brand book built in Improvement 3 will match the citations |
| HTML emails | Images and their colours | Text, `<img>` alt text and CSS colours are checked; **remote images are not downloaded** | No outbound fetches from the server; upload an image itself for its visual review |
| Public API | Not specified for images | `/api/v1/preflight/file` takes text documents only and explains that images are reviewed in the web app | OCR takes seconds per image on the free host; the web app shows progress |
| Logo clear space | "Declare as a limitation if unreliable" | Implemented (VIS-03), precision 1.00 / recall 1.00 on the labelled set | A median-filtered ring around the detected lockup proved reliable on our assets |
